# REQ-011：附件（composer 文件/图片上传）

- 状态：已验证（TEST-011 全部通过）
- 关联：DESIGN-011 · TEST-011 · FEATURE-MATRIX 行 `界面/client-ui-attachment`
- 日期：2026-10-30
- 证据：活体核对 `docs/evidence/LIVE-UI-2026-10-30.md` §4——composer
  **"Add files or run commands"（＋）**；webapp readme（minimal preset）：
  "图片读取…要求模型支持图片输入"；OpenAI 兼容多模态 content 数组格式。

## 1. 背景

mygo 的消息是纯文本：用户想让模型看一段本地代码/日志/配置，只能粘贴；图片完全无法
提供。DSH 支持附件上传（文本注入 + 图片走多模态 content）。REQ-007 已把 Shell 输出
落盘并提示 read_file 读取——附件是同一需求的输入侧。

## 2. 用户故事

作为用户，我在输入框点 ＋ 添加一个文件（相对工作区路径或系统文件对话框），文本文件
随消息注入（带路径头），图片作为多模态 image part 发送给支持视觉的模型；发送前能
预览和移除附件。

## 3. 功能需求（FR）

- **FR-1（添加）**：＋ 按钮弹 Popover：路径输入（相对工作区，回退数据目录）+「添加」；
  窗口模式另有「选择文件…」调系统文件对话框（mygo.Dialog）；无头/对话框取消静默返回。
- **FR-2（校验与读取）**：添加即校验存在；图片（png/jpg/jpeg/gif/webp）读字节上限
  8MB；文本读内容上限 64KB（超出截断注明）；超限/不存在报错不加入。
- **FR-3（预览与移除）**：输入框上方显示附件 chip（名称 + × 移除）；发送后清空。
- **FR-4（注入）**：文本附件以 `[附件：<名>]\n```<扩展名>\n<内容>\n```` 追加到消息
  文本；图片以 OpenAI 多模态 content 数组（`image_url` data URL）发送——消息含图片
  时 content 为数组（text part + image parts），纯文本消息保持字符串不变。
- **FR-5（显示与留痕）**：用户消息气泡显示附件 chip；轨迹 user 事件记录附件名单；
  history.json 按线格式持久化（恢复会话后多模态消息可重发）。
- **FR-6（协议）**：llm.Message 支持多模态（本地 Parts 字段，序列化为 content 数组），
  对纯文本消息的线上格式零影响。

## 4. 非功能需求

- **NFR-1** 图片 base64 仅在内存与 history 中存在，不在附件目录另存副本。
- **NFR-2** 读取在 UI 线程同步完成（本地文件，毫秒级），无异步复杂度。

## 5. 验收标准

- AC-1：文本附件流：添加 → chip 可见 → 发送 → 消息文本含 `[附件：a.txt]` 与文件
  内容；轨迹事件含附件名单；pendingFiles 清空。
- AC-2：图片附件：添加 png → 发送 → history 中该消息 content 为数组且含
  `image_url`（data URL）与文本 part；气泡显示图片名。
- AC-3：校验：不存在路径报错；>64KB 文本截断注明；>8MB 图片拒绝。
- AC-4：序列化：多模态消息 Marshal 为 content 数组（image_url 嵌套格式正确）、
  Unmarshal 还原 Parts；纯文本消息线上格式与既有完全一致。
- AC-5：`go test ./...` 全绿无回归。

## 6. 范围外

- read_image 工具（模型主动读图）——附件把图直接送进对话，工具形态留后续；
- 附件存储服务（dsh-attachment 的跨会话附件库）；office/pdf 附件解析；粘贴板图片；
- 会话间附件共享。

## 7. 决策记录

- 图片走 OpenAI 多模态数组而非注入 base64 文本：视觉模型的标准格式；纯文本模型收到
  图片 part 会由 API 显式报错（可见失败优于静默降级）。
- ＋ 入口同时提供路径输入与系统对话框：路径输入可无头测试，对话框给窗口用户；两者
  汇入同一 pendingFiles。

## 8. 风险与回退

- **风险**：大 history.json（图片 base64）→ 8MB/张上限 + 数量无上限由用户自担；
  后续可做附件外置存储。
- **回退**：不添加附件即行为与现状完全一致；Parts 序列化对纯文本零影响（测试锁定）。
