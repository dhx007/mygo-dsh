## 1. 背景与证据

DSH 的产品级插件体系 = **清单（inventory）+ 管理器（开关/详情卡片）+ 模型侧管理工具**
三层。mygo 现状只有第三层的影子：插件页和设置·内置插件分区是 11 个工具开关的平铺
列表（`app.go:1056-1093`、`app.go:1431-1453`），没有插件实体（名称/版本/分类/来源），
模型也不能查看或管理插件。

> 证据：
> - `.dsh-ref/dsh-package.json`：`dsh-plugin-manager`、`client-ui-plugin-manager`（管理器）、
>   `host-plugin-inventory` + `client-ui-settings-plugin-inventory`（清单）、`dsh-tool-cordis`
>   + `client-ui-cordis`（模型侧插件管理工具）、`cordis-plugin-loader/-group/-include`（运行时）。
> - `.dsh-ref/webapp-readme-zh.md` §按会话的 agent 设置：「只有 Host 提供可编辑的 profile 时，
>   **Creator 的插件管理工具**才会启用」——插件管理工具按预设授权。
> - `.dsh-ref/gui-index.js`：`PluginArtwork{Terminal,Subagent,Search,Loop,Default}` 五种插件
>   分类插图；启动屏「Loading plugins…」与 `manifest.plugins` 清单；`plugin card has no
>   field` ——插件以卡片（字段化）呈现在管理器里。
> - 本仓库 README 对齐表：设置已含「内置插件 / Web 插件」分区（对齐桌面版截图）。

## 2. 用户故事

作为用户，我希望插件页展示**真正的插件卡片**（中文名、描述、版本、分类、来源）并按
分类分组，一眼看清装了什么、开了什么；作为使用「创造」模式的用户，我希望模型能自己
列出、查询、启用、停用插件，替我完成插件管理。

## 3. 功能需求（FR）

- **FR-1** 内置插件注册表：每个内置插件是一个实体（id、显示名、描述、版本、分类、来源、
  挂载的工具、种类），全部 11 个工具插件 + 新增「插件管理」插件共 12 个，数据集中一处。
- **FR-2** 插件分类：按 DSH 的分类素材划分为 终端 / 文件 / 搜索 / 子代理 / 循环 / 系统
  六组；插件页与设置·内置插件分区都按分类分组渲染，组头显示分类名与计数。
- **FR-3** 插件页 UI 升级：每行 = 显示名 + 描述 + 版本/来源标记 + 开关；开关状态持久化
  （config.json 的 enabled_tools，键 = 插件 id）；顶部保留「一切皆插件」标题与底部说明。
- **FR-4** 设置·内置插件分区与插件页同源渲染（同一注册表、同一分组、同一开关语义）。
- **FR-5** 模型侧 `plugins` 工具（对应 dsh-tool-cordis）：action=list（全部插件与开关状态）、
  info（单个插件详情）、enable/disable（切换并持久化）；参数非法时返回错误说明。
- **FR-6** 按预设授权：仅 `can_manage_plugins=true` 的预设（内置 = 创造）且插件本身未被
  停用时，`plugins` 工具才挂载给模型；其余预设不可见。
- **FR-7** 「插件管理」插件自身可在插件页被停用（停用后创造模式的模型失去管理能力，
  用户仍可在 UI 管理）。
- **FR-8** 兼容：`enabled_tools` 旧键（= 工具名）语义不变，注册表 id 与旧键一致，无需迁移；
  四个内置预设的行为除创造模式新增工具外不变。

## 4. 非功能需求（NFR）

- **NFR-1** 注册表为唯一事实源：插件页、设置分区、模型工具、预设一致性校验全部读它，
  消除现在三处硬编码名单（`app.go` 两处 + `toolDescExtra`）。
- **NFR-2** 开关持久化路径复用 `setEnabled`（原子写 config.json），不新增存储格式。
- **NFR-3** UI 渲染保持 DSH 视觉令牌（muted 描述、11px 徽标、分组头），不动主题层。

## 5. 验收标准

- AC-1（FR-1）：注册表恰好 12 个内置插件；每个四预设引用的工具名都能在注册表找到对应插件。
- AC-2（FR-2/3/4）：ui.Tester 打开插件页，可见六个分类组头与插件显示名；切换某开关后
  config.json 的 enabled_tools 落盘正确；设置·内置插件分区渲染同一注册表。
- AC-3（FR-5）：单测——list 返回 12 项含状态；info 返回名称/版本/工具；disable bash 后
  `enabledTool("bash")==false`；enable 恢复；非法 action 报错。
- AC-4（FR-6）：预设接线——创造模式 agent 带 PluginTool 且 spec 可见；标准模式无；
  停用「插件管理」插件后创造模式也不再挂载。
- AC-5（FR-7/8）：`go test ./...` 全绿，现有 UI 测试（含设置保存、插件页既有断言）不回归。

## 7. 决策记录

- 插件粒度取**一工具一插件**（bash、read_file…各自是插件）：与既有 enabled_tools 键、
  插件页现状、DSH「预设编辑子插件」粒度一致；不以「功能域」合并成大插件。
- 分类集采 DSH 素材命名（终端/子代理/搜索/循环）+ 补 文件/系统 两类收纳其余工具，
  未在证据中的分类在 DESIGN 里声明为合理假设。
- `plugins` 工具放 agent 层回调（同 task 模式）而非 tools 包：它需要 app 的注册表与
  配置写权限，且仅特定预设挂载，与 `todo`/`task` 的动态 spec 机制同构。
